# Day 002: Temporary User Setup with Expiry

**Difficulty:** Beginner | **Time:** 15 minutes | **Category:** Linux Administration

## Objective

Create a temporary Linux account that automatically expires on an agreed date, permit only secure login, verify the result, and manage the account through its lifecycle.

> Run these commands on the target Linux server with an account that has `sudo` access. Account expiry disables login after the specified date; it does **not** remove the account or its files.

## 1. Choose and validate the account details

Use a lowercase name and an expiry date in `YYYY-MM-DD` format. The date must be in the future. Do not reuse this example key; use the user's actual public key.

```bash
TEMP_USER=yousuf
EXPIRY_DATE=2026-12-31       # Replace with the approved end date
USER_PUBLIC_KEY='ssh-ed25519 AAAA... approved-user@workstation'

if getent passwd "$TEMP_USER" >/dev/null; then
  echo "Choose a different user name" >&2
  exit 1
fi
date -d "$EXPIRY_DATE" >/dev/null || { echo "Invalid expiry date" >&2; exit 1; }
[ "$(date -d "$EXPIRY_DATE" +%s)" -gt "$(date +%s)" ] || {
  echo "Expiry date must be in the future" >&2
  exit 1
}
```

For the original KodeKloud lab, the requested command is:

```bash
sudo useradd --create-home --expiredate 2024-01-28 yousuf
```

Because `2024-01-28` is now in the past, it creates an already-expired account. Use a future approved date for a working account, as shown below.

## 2. Create the temporary account

Create a normal interactive account, a private user group, and a home directory. The expiry applies to the account itself.

```bash
sudo useradd \
  --create-home \
  --user-group \
  --shell /bin/bash \
  --expiredate "$EXPIRY_DATE" \
  "$TEMP_USER"
```

Do not grant `sudo` or other privileged groups unless the temporary assignment explicitly requires them. Add only the least-privileged group needed for the work, for example:

```bash
sudo usermod --append --groups project-dev "$TEMP_USER"
```

## 3. Configure secure login

Prefer an SSH key over a password. This setup prevents password logins for this account while allowing its approved public key. It does not require a risky, server-wide SSH configuration change.

```bash
sudo install --directory --owner "$TEMP_USER" --group "$TEMP_USER" --mode 0700 \
  "/home/$TEMP_USER/.ssh"
printf '%s\n' "$USER_PUBLIC_KEY" | sudo tee "/home/$TEMP_USER/.ssh/authorized_keys" >/dev/null
sudo chown "$TEMP_USER:$TEMP_USER" "/home/$TEMP_USER/.ssh/authorized_keys"
sudo chmod 0600 "/home/$TEMP_USER/.ssh/authorized_keys"

# Disable password authentication for this account. Public-key authentication remains available.
sudo passwd --lock "$TEMP_USER"
```

If local or password-based access is explicitly required, set a unique password interactively and apply an aging policy instead of leaving a permanent password:

```bash
sudo passwd "$TEMP_USER"
sudo chage --mindays 1 --maxdays 30 --warndays 7 --inactive 7 "$TEMP_USER"
```

The account-expiry date set with `useradd --expiredate` is separate from password aging. Keeping both policies explicit avoids accounts surviving longer than their authorized assignment.

## 4. Verify the account and expiry

Use `getent` rather than reading `/etc/passwd` directly: it also works when users are supplied by LDAP or another name service.

```bash
# Confirm identity, home directory, shell, and group membership
getent passwd "$TEMP_USER"
id "$TEMP_USER"

# Confirm the exact account expiry and password-aging policy
sudo chage --list "$TEMP_USER"

# Expected while key-only login is configured: password status begins with LK
sudo passwd --status "$TEMP_USER"

# Confirm SSH key file ownership and permissions
sudo stat --format '%A %U:%G %n' \
  "/home/$TEMP_USER/.ssh" \
  "/home/$TEMP_USER/.ssh/authorized_keys"
```

`sudo chage --list "$TEMP_USER"` should show the selected date next to **Account expires**. Before handing over access, test the SSH key from a separate terminal and retain the current administrator session. A locked password must not be treated as proof that SSH-key access works.

## 5. Manage the account lifecycle

```bash
# Extend or shorten the agreed access period
sudo chage --expiredate 2027-01-31 "$TEMP_USER"

# Immediately suspend access without deleting the account
sudo usermod --lock --expiredate "$(date +%F)" "$TEMP_USER"

# Restore a suspended account only after re-approval
sudo usermod --unlock "$TEMP_USER"
sudo chage --expiredate 2027-01-31 "$TEMP_USER"

# Review accounts that are already expired (local-account audit)
sudo chage --list "$TEMP_USER"

# Permanently remove the account and its home directory after retention requirements are met
sudo userdel --remove "$TEMP_USER"
```

Before removing an account, archive or transfer required work according to the organization's retention policy. Never use `userdel --remove` until the exact account name and data-retention requirements have been confirmed.

## Troubleshooting

- **`useradd: user already exists`** — inspect the account with `getent passwd yousuf`; do not overwrite an existing user.
- **Expiry date is rejected** — use ISO format (`YYYY-MM-DD`) and confirm the server clock with `date`.
- **SSH key is ignored** — verify `.ssh` is `0700`, `authorized_keys` is `0600`, and both are owned by the temporary user. Check the SSH service logs with `journalctl -u sshd` (or `journalctl -u ssh`).
- **Account cannot log in** — inspect `sudo chage --list yousuf`, verify it has not expired, and check whether it is intentionally password-locked.

## Key Takeaways

- `useradd --expiredate` provides a clear end date for temporary access.
- Key-based authentication and least-privilege groups reduce exposure during the assignment.
- `chage --list` is the authoritative, human-readable expiry check.
- Expiry disables access but does not perform data cleanup; suspension, retention, and deletion are distinct lifecycle stages.
