# Day 003: Secure SSH Root Access

**Difficulty:** Beginner | **Time:** 15 minutes | **Category:** Linux Security

## Objective

Disable direct SSH login as `root` on every application server. Administrators should sign in with their individual account and use `sudo` for privileged work, keeping an attributable audit trail.

> Keep the current administrative SSH session open until a new, non-root login and `sudo` access have both been tested. Without another working administrator account or console access, an SSH change can lock you out of the server.

## 1. Confirm a safe administrative path

Before changing the SSH configuration, confirm that an authorized non-root account can log in and use `sudo`:

```bash
whoami
sudo -v
sudo -l
```

If this is a new server, configure and test that account first. Prefer SSH keys and unique user accounts over a shared administrator account.

## 2. Disable root SSH login

On the KodeKloud application servers, the requested setting is `PermitRootLogin no`. Create a dedicated SSH configuration drop-in so the change is clear and easier to manage than editing the vendor-supplied file directly:

```bash
sudo install --directory --mode 0755 /etc/ssh/sshd_config.d
printf '%s\n' 'PermitRootLogin no' | \
  sudo tee /etc/ssh/sshd_config.d/99-disable-root-login.conf >/dev/null
```

If the server does not load `/etc/ssh/sshd_config.d/*.conf`, edit `/etc/ssh/sshd_config` instead and set the effective value to:

```text
PermitRootLogin no
```

Use one active `PermitRootLogin` setting. A conflicting setting in another included file can override the intended policy, depending on the distribution's OpenSSH configuration order.

For the original lab, the equivalent direct edit and restart are:

```bash
sudo sed -i 's/^[[:space:]]*#\?[[:space:]]*PermitRootLogin.*/PermitRootLogin no/' \
  /etc/ssh/sshd_config
```

The drop-in approach above is generally safer because it does not alter the distribution-managed configuration file. Do not use the `sed` command if a drop-in is already setting this option.

## 3. Validate and reload SSH

Validate the configuration before reloading the service:

```bash
sudo sshd -t
```

No output means the syntax is valid. If an error is shown, fix it before continuing. Then reload the service without disconnecting existing sessions:

```bash
# RHEL, CentOS, Rocky, AlmaLinux, and most KodeKloud labs
sudo systemctl reload sshd

# Debian or Ubuntu systems commonly use this service name instead
# sudo systemctl reload ssh
```

If `reload` is unavailable, use `sudo systemctl restart sshd` only after the configuration check succeeds.

## 4. Verify the effective policy

Check the server's effective OpenSSH configuration rather than relying only on the file contents:

```bash
sudo sshd -T | grep '^permitrootlogin '
# Expected: permitrootlogin no

sudo systemctl is-active sshd
```

From a separate terminal, test the normal administrator login:

```bash
ssh admin-user@app-server
sudo whoami
# Expected: root
```

Then confirm that direct root SSH login is rejected:

```bash
ssh root@app-server
# Expected: Permission denied (publickey,password,...)
```

Do not close the original session until the non-root test succeeds.

## Apply the policy to several application servers

For a small, known list of servers, use your existing administrator account and apply the same validated commands one host at a time. Replace the host names and account name before running this:

```bash
for server in app1 app2 app3; do
  ssh admin-user@"$server" \
    'sudo install --directory --mode 0755 /etc/ssh/sshd_config.d &&
     echo "PermitRootLogin no" | sudo tee /etc/ssh/sshd_config.d/99-disable-root-login.conf >/dev/null &&
     sudo sshd -t &&
     sudo systemctl reload sshd &&
     sudo sshd -T | grep "^permitrootlogin no$"'
done
```

In a production environment, apply this through reviewed configuration management (such as Ansible) and retain console access or an approved rollback path for every host.

## Troubleshooting and rollback

- **`sshd -t` reports an error:** do not reload SSH. Inspect the named file and correct the syntax.
- **The service is named `ssh`:** use `sudo systemctl reload ssh` and `sudo systemctl is-active ssh`.
- **The effective value is not `no`:** search the main configuration and included files for another `PermitRootLogin` directive: `sudo grep -RIn -- '^[[:space:]]*PermitRootLogin' /etc/ssh`.
- **You lost non-root access:** use the provider console or a remaining session, remove the drop-in with `sudo rm /etc/ssh/sshd_config.d/99-disable-root-login.conf`, validate with `sudo sshd -t`, and reload SSH. Restore root access only long enough to repair the authorized administrator path.

## Key Takeaways

- `PermitRootLogin no` prevents direct SSH authentication as `root`.
- Individual SSH accounts plus `sudo` improve accountability and reduce the attack surface.
- Test OpenSSH configuration before reload, and verify the effective configuration afterward.
- Preserve a tested non-root administrator route before changing remote access controls.
